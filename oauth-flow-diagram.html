Cross-workspace U2M via OAuth app connection

How the FDE app (Workspace B) gets a token that Workspace A accepts as the real user — the flow behind buttons 5 & 6.

Front-channel — through the user's browser (needs login UI + WS A cookies) Back-channel — server-to-server HTTP from the FDE app
Step-by-step
  1. ① You click App · U2M (OAuth) → browser hits the FDE app's /oauth/start.
  2. ② FDE app doesn't call anything — it returns a 307 telling the browser to go to WS A's /oidc/v1/authorize, carrying the client_id, redirect_uri, requested scope, a random state, and a PKCE code_challenge.
  3. ③ The browser calls WS A's authorize endpoint. WS A shows login/consent (using the browser's WS-A session), and checks the redirect_uri against the app connection's registered list.
  4. ④ WS A redirects the browser back to the FDE app's /oauth/callback with a short-lived code — and only to the pre-registered URL.
  5. ⑤ Browser delivers the code to the FDE app.
  6. ⑥ FDE app (server-side) POSTs the code + PKCE code_verifier to WS A's /oidc/v1/token.
  7. ⑦ WS A returns a WS-A-issued user access token (iss/aud = WS A).
  8. ⑧ FDE app calls the GTM app's /api/gtm-summary with that token.
  9. ⑨ Because the token was minted by WS A, WS A accepts it and the GTM app sees the real user.
  10. ⑩ FDE app renders the result banner.
Why this is different from the other two buttons

M2M (buttons 1, 3)

A service principal gets a token from WS A via client-credentials (wrapped in a UC connection). WS A sees the SP, not a human. Works cross-workspace.

U2M — forward (2, 4)

Reuse the user's WS-B token against WS A. Its iss/aud are WS-B → WS A rejects it. 401 / Invalid Token.

U2M — OAuth (5, 6)

User logs in directly to WS A, so WS A mints the token. WS A accepts it and sees the real user. Works cross-workspace.
The crux: a token is only accepted by the workspace that minted it. Forwarding reuses the wrong workspace's token (fails); the OAuth flow makes WS A itself mint a fresh token for the user (works) — which is only possible because the app connection's client_id and redirect_uri are registered in WS A's account.
